# 后端代码规范

- Java 生产代码、测试和工具脚本均使用显式局部变量类型，不使用 `var`，包括循环变量和 try-with-resources。
- 新增或修改业务类型时使用明确的单类型导入，避免通配符导入隐藏同名冲突。核对自动导入的包，不引入与业务无关的 JDK 或第三方类型。
- 返回 DTO 使用明确的业务名称并注明用途，例如 `PublicationCardView` 是文章列表的只读返回模型，不能作为数据库实体或领域聚合使用。
- 简单数据库操作沿用 MyBatis-Plus；复杂联表投影使用 Mapper XML。跨模块能力通过端口与 composition 适配。
- HTTP JSON 返回统一使用 `Result`。类型或命名调整保持接口字段和业务行为兼容，并运行受影响的编译及测试。
- 业务规则、并发边界和重要数据约束写清楚中文注释。可复用值使用已有常量或明确命名的常量。
- 较长的业务编排按用途拆成具名步骤。公开端口说明输入、返回值和缺失值语义；分支注释说明权限、可见性、兼容或并发原因，不逐行复述赋值语句。跨领域适配器必须说明各模块负责哪些规则，避免读者自行推测。
- 固定业务编码（访问方式、状态、目标类型、事件类型、排序等）优先复用所属领域枚举，禁止在判断、查询条件或事件映射中直接重复写字符串字面量。领域内部传递枚举，持久化与旧字符串接口边界用 `name()` / `valueOf()` 转换。开放扩展的挂载目标编码由所属模块声明常量；不要把业务常量全部塞进 shared，也不要拼接字符串构造事件类型。注解要求编译期常量的校验规则与默认值集中声明，并测试它们与枚举保持一致。

- 文章详情、评论挂载及动态目标统一使用数据库 ID，不生成或兼容文章 slug。分类 slug 仅用于分类筛选。当前开发阶段的结构调整直接统一契约与数据，不自行增加旧接口回退分支。
